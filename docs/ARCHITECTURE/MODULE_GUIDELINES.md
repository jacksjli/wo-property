# 模块化设计原则

> **版本**：v1.0
> **日期**：2026-05-06
> **状态**：已确认

---

## 核心理念

模块化设计的核心目标：
1. **高内聚** — 模块内部紧密相关
2. **低耦合** — 模块之间依赖最小化
3. **可替换** — 模块可以独立演进

---

## 原则一：新增模块

### 前置要求
- [ ] 理解并遵守 `ARCHITECTURE/` 下的所有全局规范
- [ ] 理解服务间通信协议 (`SERVICE_COMMUNICATION.md`)
- [ ] 理解数据库设计规范 (`DATABASE_DESIGN.md`)
- [ ] 理解字段命名规范 (`FIELD_NAMING.md`)

### 执行步骤

```
1. 定义模块边界
   - 明确模块职责范围
   - 定义公开 API 接口
   - 声明对其他模块的依赖

2. 创建模块文档
   - docs/MODULES/{module}/DESIGN.md      — 模块设计
   - docs/MODULES/{module}/API.md         — API 定义
   - docs/MODULES/{module}/FIELDS.md      — 字段说明
   - docs/MODULES/{module}/CHANGELOG.md   — 变更记录

3. 实现与测试
   - 遵循 CODING_STANDARDS.md
   - 遵循 API_DESIGN.md
   - 编写单元测试

4. 上线检查
   - [ ] 全局规范符合性检查
   - [ ] 对其他模块无破坏性影响
   - [ ] 文档完整性审核
```

### 新增模块模板

```
docs/MODULES/{module}/
├── DESIGN.md      # 模块设计（必选）
├── API.md         # API 定义（必选）
├── FIELDS.md      # 字段说明（必选）
└── CHANGELOG.md  # 变更记录（必选）
```

## 原则二：删除模块

### 风险等级评估

| 等级 | 条件 | 处理方式 |
|------|------|---------|
| 🔴 高 | 其他模块有硬依赖 | 禁止删除，需先迁移依赖 |
| 🟠 中 | 仅前端菜单引用 | 先取消菜单，再删除后端 |
| 🟢 低 | 完全独立模块 | 按流程删除 |

### 执行步骤

```
1. 影响分析
   - 检查其他模块的代码依赖（grep -r "moduleName"）
   - 检查数据库外键关联
   - 检查前端 API 调用
   - 检查 shared fieldConfig 引用

2. 数据处理
   - 评估数据迁移方案
   - 或数据归档方案
   - 确保审计日志完整

3. 依赖解除
   - 移除其他模块的 import/require
   - 更新前端的 module 配置
   - 更新全局 fieldConfig

4. 删除执行
   - 删除后端服务目录
   - 删除前端 views/api/stores
   - 更新 docker-compose.yml
   - 从 allModules 移除

5. 文档处理
   - 将模块文档移至 docs/MODULES/_deprecated_/
   - 保留变更记录供追溯
```

### 删除前检查清单

```
□ 其他模块是否引用本模块的 API？
□ 其他模块是否引用本模块的数据库表？
□ 其他模块是否引用本模块的枚举值？
□ 前端是否还在调用本模块的接口？
□ 是否有定时任务或 cron 依赖本模块？
□ 是否有告警或监控依赖本模块？
```

## 原则三：修改模块

### 变更分类

| 类型 | 定义 | 影响范围 |
|------|------|---------|
| **破坏性变更** | 删除 API、删除字段、修改字段类型 | 需要版本升级 |
| **非破坏性变更** | 新增 API、新增字段 | 向后兼容 |
| **配置变更** | 默认值、枚举值 | 需评估影响 |

### 执行步骤

```
1. 影响评估
   - 识别变更涉及的 API
   - 评估对调用方的影响
   - 记录需要的同步修改

2. 变更分级
   - 破坏性变更 → 需创建 v2 版本，旧版本兼容
   - 非破坏性变更 → 直接执行
   - 配置变更 → 评估后执行

3. 协同通知
   - 通知相关模块负责人
   - 提供变更窗口
   - 准备回滚方案

4. 执行与验证
   - 执行数据库迁移（如有）
   - 更新模块文档
   - 执行集成测试

5. 上线与监控
   - 灰度发布（如有必要）
   - 监控错误率
   - 准备回滚
```

### 修改前检查清单

```
□ 此次变更是否影响其他模块的 API 调用？
□ 是否需要同步修改调用方？
□ 是否需要数据库迁移？
□ 是否需要更新 fieldConfig？
□ 是否有前端硬编码需要修改？
□ 是否需要通知甲方？
```

## 模块依赖管理

### 允许的依赖关系

```
允许：
  业务服务 → 公共服务（PersonService, MasterDataService）
  业务服务 → AuthService
  前端 → 公共服务 API

禁止：
  业务服务 → 其他业务服务（横向调用）
  公共服务 → 业务服务
```

### 依赖检查命令

```bash
# 检查模块间依赖
grep -r "localhost:50" src/WO.Property.{Module}/ | grep -v "PersonService\|MasterDataService"

# 检查前端 API 调用
grep -r "api/" src/admin-portal/src/api/ | grep -i "{module}"
```
